# 09.03 6차시 발표 대본

> 예상 시간: 약 4분
>
> 발표 화면: `docs/load-recovery-assignment.md`

## 1. 결과 요약

**화면:** `먼저 보는 결론`

안녕하세요. 이번에는 기존 부하·복구 결과를 보완하고, 지금까지 만든 파이프라인이 실제로 어디까지 이어지는지 점검했습니다.

현재 두 경로가 있습니다. 첫 번째는 실제 원시 체결을 Parquet에서 읽어 Kafka, Spark, PostgreSQL로 보내는 검증 경로입니다. 두 번째는 공식 경제 발표를 기준으로 Alpaca의 분석용 1분봉과 일봉을 수집하는 경로입니다.

## 2. 부하 실행과 식별키 수정

**화면:** `1. 정상 입력과 결과`, `2. 더 큰 입력과 실행 환경`

기준은 CPI 한 번과 네 종목의 SIP 체결 118,118건입니다. Kafka 발행·수신과 Spark 입력이 같았고 PostgreSQL에는 472개 1분봉을 저장했습니다.

이를 CPI 55회로 확대해 실제 체결 7,360,804건을 GCP에서 처리했습니다. 실행 시간은 약 28분 10초였고 최종 1분봉은 22,260행이었습니다.

여기서 기존 결과를 다시 점검하면서 중요한 오류를 발견했습니다. 당시 Spark가 중복이라고 표시한 49건은 실제 중복이 아니었습니다. 같은 종목, 거래 ID와 시각을 가지지만 거래소가 다른 별개의 체결이었습니다. 기존 `event_id`에 거래소가 빠져 있었기 때문에 발생한 충돌입니다.

식별키에 거래소를 추가하고 보존한 Parquet 원본 7,360,804건을 Kafka부터 전체 재실행했습니다. 수정 후에는 Kafka 발행·수신·Spark 입력이 모두 7,360,804건이고, 형식 오류와 실제 중복은 0건입니다. 최종 1분봉 22,260행과 DB 고유키 중복 0건도 다시 확인했습니다.

## 3. 장애와 복구

**화면:** `3. 실패 원인과 탐지`, `4. 재실행 위치와 무결성`

처음에는 Spark가 여러 단계에서 사용하는 중간 결과를 메모리에 두면서 Java heap 부족이 발생했습니다. 입력 파일 자체가 6GB라는 뜻이 아니라 Spark 작업 메모리 한도를 넘었다는 뜻입니다. 중간 결과를 VM 디스크에 두는 `DISK_ONLY`로 바꾼 뒤 전체 범위를 끝까지 처리했습니다.

PostgreSQL 컨테이너를 중지했을 때는 Kafka 전송 후 DB 적재 단계가 실패로 기록됐습니다. DB를 다시 시작하고 기준 입력의 Kafka 재생부터 다시 실행했습니다. Upsert를 사용했기 때문에 최종 22,260행은 늘어나지 않았고 중복도 0건이었습니다.

API 장애는 외부 서비스가 아니라 로컬 mock으로 안전하게 확인했습니다. 첫 요청에서 503을 반환하자 작업 실패와 alert OPEN이 기록됐고, 합성 fixture로 재시도한 뒤 성공과 RESOLVED로 바뀌었습니다. 이 fixture는 장애 제어만 확인하며 실제 시장 데이터로 사용하지 않습니다.

## 4. 77회·10종목과 Airflow

**화면:** `경제 이벤트·10종목 분석용 bar`, `실제 Airflow event-symbol 실행`

분석 데이터는 CPI, 고용, PCE, FOMC 77회와 10종목으로 넓혔습니다. 발표 전 60분부터 발표 후 120분까지의 1분봉은 117,566행이고, 여기서 3분봉 43,184행과 5분봉 26,883행을 만들었습니다. 발표 전후 7거래일 일봉은 고유키 기준 8,740행입니다.

이번에는 이 수집 코드를 Airflow에 연결했습니다. 실행 단위는 경제발표 1건과 종목 1개이며, 한 종목이 실패해도 실패 범위와 재실행 위치를 구분할 수 있습니다.

FOMC 2026년 7월 29일과 SPY, TLT로 실제 실행했습니다. 종목마다 1분봉 181개, 3분봉 61개, 5분봉 37개와 일봉 15개가 저장돼 합계는 588행입니다. 동일 입력을 다시 실행해도 588행과 결과 hash가 같았고 DB 중복은 0건이었습니다.

## 5. 현재 경계와 다음 단계

**화면:** `5. 현재 실제 연결과 남은 작업`

현재 수집, Kafka 전달, Spark 전처리, PostgreSQL 저장, Airflow 작업 분리, 재실행과 alert 상태까지 확인했습니다.

아직 전체 770개 작업을 새 DAG으로 다시 실행하지는 않았습니다. Kafka의 97.5% 파티션 쏠림을 개선할 key와 파티션 수 비교, 고용·PCE·FOMC 실제 발표값의 point-in-time 결합, 전체 영향 분석과 거래비용을 포함한 백테스트도 다음 단계입니다.

이번 제출의 핵심은 성공 화면만 추가한 것이 아니라, 식별키 오류를 찾아 원본으로 전체를 다시 처리했고 단계별 건수와 최종 무결성을 다시 증명했다는 것입니다. 감사합니다.
