# 09.03 6차시 발표 대본

> 예상 시간: 약 4분
>
> 발표 화면: [`pipeline-review-assignment.md`](pipeline-review-assignment.md)

## 1. 전체 결과

**화면:** 문서 맨 위와 `최신 전체 흐름` 그림

안녕하세요. 이번에는 지난 부하·복구 실험을 다시 하는 대신, 수업에서 설명이 부족했던 부분과 전체 파이프라인의 정확성을 보완했습니다.

현재 흐름은 실제 CPI 발표 일정과 당시 경제지표, Alpaca SIP 체결을 연결하는 구조입니다. 원시 체결은 Parquet으로 보관하고, Kafka로 전달한 뒤 Spark가 검증과 1분봉 집계를 수행하고 PostgreSQL에 저장합니다. Airflow는 종목과 시간 범위를 입력받아 다종목 작업 순서를 관리합니다.

수정 후 전체 결과는 원시 체결 7,360,804건, Kafka 발행과 수신 각각 7,360,804건, Spark 입력 7,360,804건입니다. 형식 오류와 실제 중복은 모두 0건이고 PostgreSQL에는 1분봉 22,260행이 있으며 고유키 중복은 0건입니다.

## 2. 기준과 부하 실행

**화면:** `기준·부하·수정 후 실행 비교` 표

기준 실행은 2026년 8월 12일 CPI 한 번과 네 종목의 체결 118,118건이고, 부하 실행은 2022년부터 2026년 8월까지 CPI 55회와 네 종목의 7,360,804건입니다. 입력이 약 62배 증가했습니다.

GCP 부하 실행은 1,690초, 약 28분이 걸렸고 평균 처리량은 초당 약 4,355건이었습니다. 수정 후 전체 재실행은 로컬에서 수행했기 때문에 두 실행 시간을 직접적인 성능 비교로 보지는 않습니다. 중요한 것은 두 실행 모두 Kafka 발행·수신과 Spark 입력 건수가 원시 입력과 일치한다는 점입니다.

## 3. 점검 중 발견한 문제와 수정

**화면:** `발견한 결함과 복구`

이번 점검에서 가장 중요한 보완은 기존에 중복이라고 설명했던 49건입니다. 원본을 다시 비교해 보니 실제 중복이 아니라, 거래소가 다른 별개의 체결이었습니다.

기존 거래 식별키에는 종목, 거래 ID와 시각은 있었지만 거래소가 빠져 있었습니다. 그래서 다른 거래소에서 같은 ID와 시각을 사용한 체결을 같은 거래로 잘못 판단했습니다.

식별키에 거래소를 추가한 뒤 Parquet 원본 7,360,804건을 전수 검사했고 충돌은 0건이었습니다. 이어서 Kafka부터 PostgreSQL까지 전체를 다시 처리해 Spark 중복 0건, 최종 1분봉 22,260행, DB 고유키 중복 0건을 확인했습니다.

이 문제를 복구할 수 있었던 이유는 집계 전 원시 체결을 Parquet에 보존했기 때문입니다. 외부 API를 다시 호출하지 않고 저장 원본부터 전체 결과를 다시 만들 수 있었습니다.

## 4. 장애 복구와 fallback

**화면:** `장애·복구와 fallback`

DB 장애는 GCP에서 PostgreSQL 컨테이너만 중지해 재현했습니다. Kafka는 118,118건을 정상적으로 발행하고 수신했지만 DB 적재에서 `OperationalError`가 발생했고 저장 건수는 0으로 기록됐습니다.

PostgreSQL을 다시 시작한 뒤 같은 기준 입력을 재실행하자 472개의 1분봉이 Upsert됐습니다. 기존 고유키를 갱신했기 때문에 전체 22,260행은 늘어나지 않았고 중복도 0건이었습니다.

API fallback은 외부 서비스에 장애를 만들지 않고 mock 응답을 사용했습니다. 첫 요청이 503을 반환하자 한 번 재시도했고, 두 번째 정상 JSON을 받아 `recovered=true`가 된 것을 확인했습니다. 운영 알림은 아직 구현하지 않았고 이번 제출에서는 실제 retry fallback 결과를 제시합니다.

## 5. 확인 방법과 남은 작업

**화면:** `단계별 실행 증거와 확인 방법`, 이어서 `아직 실행되지 않는 단계`

Airflow는 네 종목 task 성공 화면과 입력을 바꾼 재실행 화면이 있습니다. Kafka와 Spark는 수정 후 실행 JSON에서 단계별 건수를 확인하고, PostgreSQL은 SQL 결과로 22,260행, 고유키 중복 0건과 결과 hash를 확인합니다.

아직 대량 GCP 실행을 Airflow에서 발표일별로 재개하는 구조, 운영 alert, 5분봉과 coverage, 다른 경제 이벤트, BI나 API는 구현하지 않았습니다. 현재 완료 범위와 계획을 문서에서 분리했습니다.

정리하면 이번 보완에서는 단순히 성공 화면을 추가한 것이 아니라, 기존 중복 판정의 오류를 찾아 식별키를 수정했고, 보존 원본으로 전체 파이프라인을 다시 실행해 최종 결과의 무결성을 다시 확인했습니다. 감사합니다.
