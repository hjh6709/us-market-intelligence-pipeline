# 2차시 과제 발표 대본

예상 시간: 약 4분

## 1. 프로젝트 소개

안녕하세요. 제 프로젝트는 **미국 경제지표 발표 전후에 주식시장이 어떻게 움직였는지 검증할 수 있는 데이터 파이프라인**입니다.

장기적으로는 이 결과를 자동매매 전략 연구에 활용하고 싶습니다. 다만 지금 바로 주문 기능을 만드는 것이 아니라, 먼저 판단에 사용할 데이터를 안정적으로 수집하고 저장하는 것이 이번 과제의 목표입니다.

## 2. 사용하는 데이터

데이터는 목적에 따라 나눴습니다.

Alpaca의 실시간 WebSocket에서는 미국 주식 거래 데이터를 받습니다. 무료 IEX 데이터이기 때문에 전체 시장을 대표하는 확정 신호가 아니라, 실시간 파이프라인을 검증하고 이상 움직임을 빠르게 발견하는 용도로 사용합니다.

장 종료 후에는 Alpaca Historical API의 더 넓은 과거 데이터를 이용해 같은 시간대의 움직임을 다시 확인할 계획입니다.

그리고 FRED와 미국 정부기관의 공식 자료에서 CPI, 고용, 금리 같은 경제지표 값과 발표 시각을 수집합니다. 이 데이터를 주가 데이터와 시간 기준으로 연결해서 발표 전후 5분, 30분, 60분의 가격, 거래량, 변동성 변화를 비교하려고 합니다.

## 3. 전체 데이터 흐름

전체 흐름은 이렇습니다.

실시간 거래 데이터가 들어오면 수집 프로그램이 Kafka에 전달합니다. Kafka는 수집과 처리를 분리하고, 처리 프로그램이 잠시 중단돼도 데이터를 다시 읽을 수 있게 해줍니다.

Spark는 개별 거래를 종목별 1분봉으로 묶고, 중복과 늦게 도착한 데이터를 처리합니다. 최종 결과는 PostgreSQL에 저장해서 SQL로 조회할 수 있게 합니다.

Airflow는 실시간 경로가 아니라 경제지표와 과거 시장 데이터를 일정에 맞춰 수집하고, 실패한 작업을 재실행하는 배치 작업에 사용할 예정입니다.

즉, 지금 구현한 핵심 흐름은 **Alpaca → Kafka → Spark → PostgreSQL**입니다.

## 4. 현재 구현과 검증 결과

말로만 설계한 것이 아니라 실제 데이터로 단계별 확인도 했습니다.

먼저 미국 정규장에서 Alpaca WebSocket의 실제 IEX 거래 10건을 받아 Kafka에 넣고 다시 읽는 것까지 확인했습니다.

또 장이 끝난 뒤에도 같은 처리 경로를 검증할 수 있도록 Alpaca Historical API에서 SMH 실제 거래 427건을 가져와 Kafka에 발행했습니다. 이 실행에서 watermark를 통과한 실제 거래 174건과 거래량 6,914가 PostgreSQL의 최종 1분봉 3건에 반영됐고, 중복 키는 0건이었습니다.

자동 테스트는 45개가 통과했습니다. Kafka와 Spark 통합 테스트에서는 늦게 도착한 이벤트가 최종 결과에서 제외되는 것도 확인했고, PostgreSQL을 잠시 사용할 수 없는 상황에서는 실패를 기록한 뒤 복구 후 같은 작업을 다시 처리하는 시나리오도 검증했습니다.

여기서 중요한 점은 실시간 WebSocket 데이터는 현재 Kafka까지, Historical 실제 데이터는 PostgreSQL 저장까지 검증했다는 것입니다. 실시간 전체 저장 경로가 끝났다고 과장해서 말하지 않겠습니다.

## 5. 다음 단계와 피드백 질문

다음 단계는 미국 정규장에 WebSocket부터 PostgreSQL까지 한 번에 실행해 실시간 전체 경로를 검증하는 것입니다. 그다음 경제지표와 과거 시장 데이터를 Airflow로 수집하고, 발표 전후 주가 반응을 비교하는 분석 테이블을 만들겠습니다.

멘토님께는 두 가지를 여쭙고 싶습니다. 첫째, 현재 규모에서도 Spark를 학습 목적으로 유지하는 것이 적절한지, 아니면 처리량 비교 결과에 따라 Python 처리기와 비교하는 것이 좋은지 궁금합니다. 둘째, 원본 거래를 Kafka에 24시간 보관하는 현재 정책이 과제 범위에 적절한지도 피드백받고 싶습니다.
