# 발표 예상 질문과 짧은 답변

## 프로젝트 목표가 이상 탐지인가요, 자동매매인가요?

이번 4주 프로젝트의 목표는 경제지표 발표 전후의 시장 반응을 검증할 수 있는 데이터 파이프라인입니다. 자동매매는 장기 목표이며, 이번에는 주문 API를 호출하지 않습니다.

## 거래량이 늘어난 종목만 찾는 프로젝트인가요?

아닙니다. 가격 수익률, 거래량, 변동성을 함께 계산하고 평소 같은 시간대, 시장 ETF, 업종 ETF, 과거의 같은 발표와 비교합니다. 한 번의 움직임만 보고 경제지표가 원인이라고 단정하지 않습니다.

## FRED는 어디에 사용하나요?

CPI, 고용, 금리 같은 거시경제 지표 값과 과거 수정 이력을 가져오는 데 사용합니다. 정확한 발표 시각은 BLS, BEA, Federal Reserve 같은 공식 기관 일정에서 별도로 가져옵니다.

## 왜 yfinance가 아니라 Alpaca인가요?

현재 과제는 안정적인 실시간 수집과 메시지 단위 처리가 중요합니다. Alpaca는 인증된 Market Data API와 주식 WebSocket 계약을 공식 문서로 제공하므로 수집 코드와 장애 처리를 명확히 설계할 수 있습니다. yfinance는 향후 보조 검증이나 탐색에 사용할 수 있지만 현재 실시간 수집 경로의 정본으로 두지 않습니다.

## 무료 IEX 데이터로 시장 분석이 가능한가요?

IEX는 미국 전체 거래소 데이터가 아니므로 실시간 결과를 전체 시장의 확정 신호로 사용하지 않습니다. 실시간 파이프라인과 예비 신호를 확인하는 데 사용하고, 장 종료 후 이용 가능한 historical SIP 데이터로 사후 검증할 계획입니다.

## SIP가 무엇인가요?

미국 여러 거래소의 거래·호가 정보를 모아 통합한 시장 데이터입니다. 한 거래소만 보는 IEX보다 전체 시장을 확인하기에 적합합니다.

## 15분 이상 지난 SIP 데이터도 의미가 있나요?

실시간 알림에는 늦지만, 경제지표 발표 전후 반응을 사후 분석하고 백테스트하는 데는 의미가 있습니다. 프로젝트에서는 IEX를 실시간 예비 신호, historical SIP를 사후 검증으로 역할을 나눕니다.

## 왜 Kafka를 사용하나요?

수집기와 처리기를 분리하고, Spark나 DB가 잠시 멈춰도 보관된 이벤트를 다시 처리하기 위해서입니다. 여러 소비자를 추가하거나 replay 부하 테스트를 하기에도 적합합니다.

## 이 규모에 Spark가 꼭 필요한가요?

현재 22종목 규모에는 Python 처리기도 충분할 가능성이 큽니다. 다만 과정의 필수 기술이고 event-time, watermark, window 집계를 직접 검증하기 위해 사용합니다. 이후 replay 부하 테스트로 Python 방식과 비교해 실제 필요성을 설명하겠습니다.

## Airflow는 실시간 처리에 사용하나요?

아닙니다. 실시간 데이터는 Kafka와 Spark가 처리합니다. Airflow는 경제지표, 과거 시장 데이터, 재수집과 backfill처럼 일정과 작업 의존성이 필요한 배치 흐름을 담당합니다.

## 1,576건이 왜 1분봉 18건이 됐나요?

Spark append mode가 2분 watermark를 통과한 분만 저장하기 때문입니다. 분석 대상 거래는 509건이고 모두 18개 최종 봉에 반영됐습니다. 나머지 1,067건은 마지막 분석 봉을 확정하기 위해 붙인 3분 tail의 거래이며 validation 오류나 유실이 아닙니다.

## WebSocket으로 PostgreSQL까지 저장한 결과인가요?

아직 아닙니다. WebSocket 실제 거래 10건은 Kafka 발행과 재소비까지 확인했습니다. PostgreSQL의 18개 1분봉은 2026-08-12 CPI 발표 구간의 Historical Trades API 거래 1,576건을 Kafka에 replay하고 Spark로 집계한 결과입니다. 같은 계약의 실시간 전체 경로는 실제 발표일에 별도로 검증해야 합니다.

## 가짜 거래 데이터도 분석에 사용하나요?

아닙니다. 합성 또는 replay 데이터는 부하, 중복, 지연, 장애 복구를 재현하는 테스트 전용입니다. 경제지표 결과는 공식 자료와 실제 시장 데이터로 계산합니다.

## 원본 데이터는 어디에 얼마나 보관하나요?

원본 trade는 Kafka `raw.market.v1` 토픽에서 24시간 보관합니다. 최종 1분봉은 PostgreSQL에 저장합니다. 수년치 raw tick을 장기 저장할 필요가 생기면 Parquet와 object storage를 추가하는 방향을 검토합니다.

## 왜 GitHub에는 실제 가격 CSV가 없나요?

CPI 발표 구간의 실제 거래 1,576건을 Kafka에 발행했고, watermark를 통과한 509건이 반영된 final 봉 18개가 PostgreSQL에 있습니다. 다만 Alpaca의 시장 데이터 재배포 제한을 지키기 위해 정확한 가격 행과 원본 payload는 공개하지 않았습니다. 공개 저장소에는 실제 처리 건수, 시간 범위, 중복 결과와 합성 스키마 예시를 남겼습니다.

## 중복 저장은 어떻게 막나요?

Spark에서 거래 ID 기준 중복을 제거하고, PostgreSQL에서는 종목·봉 시작 시각·데이터 출처·feed를 business key로 삼아 unique 제약과 upsert를 적용합니다.

## 장애가 나면 어떻게 되나요?

Kafka에 원본 이벤트가 남아 있어 처리기를 다시 시작할 수 있습니다. DB 저장 실패는 오류로 기록하고 재시도하며, 복구 후 같은 batch를 다시 실행해도 unique key와 upsert 때문에 결과가 중복되지 않도록 설계했습니다.
