# 09.07 7차시 발표 대본

> 예상 시간: 약 4분
> 발표 화면: `docs/serving-layer-assignment.md`와 로컬 `Macro Pulse`

## 1. 문제와 이번에 완성한 부분

**화면:** `먼저 보는 결론`과 대시보드 캡처

안녕하세요. 지금까지는 경제 발표와 주가를 수집하고 PostgreSQL에 저장한 뒤 SQL과 로그로 결과를 확인했습니다. 이번에는 저장된 결과를 실제 사용자가 읽는 단계까지 연결했습니다.

경제 발표와 종목을 고르면 FastAPI가 PostgreSQL에서 발표 전후 주가, 당시 경제 환경과 과거 전략 결과를 읽고 이 대시보드에 보여줍니다. 새 전략을 추가한 것이 아니라, 기존 파이프라인의 마지막 출구를 만든 것입니다.

최종 목표는 자동매매지만 지금은 실주문을 보내지 않습니다. 화면의 현재 단계는 `RESEARCH_ONLY`, 실제 행동은 `NO_TRADE`입니다.

## 2. 어떤 데이터를 읽는가

**화면:** `1. 문제와 실제 데이터`의 표

데이터 범위는 2022년부터 2026년 8월까지 CPI, 고용보고서, PCE와 FOMC 발표 202회입니다. 종목은 SPY, NVDA 등 10개라서 발표와 종목의 조합은 2,020개입니다.

발표 전 60분부터 발표 후 120분까지 실제로 존재하는 SIP 1분봉 선택 합계는 308,512개입니다. 이 1분봉을 묶어 3분봉 112,593개와 5분봉 70,090개를 만들었습니다. 발표마다 FRED·ALFRED 경제지표 10개를 연결했고 발표 전후 네 구간의 시장 반응은 8,080행입니다.

이 숫자를 모두 더해 하나의 원본 건수라고 말하지 않습니다. 3분봉과 5분봉은 1분봉에서 만든 데이터이고, 가까운 발표끼리는 같은 시각의 봉을 함께 사용할 수 있기 때문입니다.

## 3. 입력부터 읽기까지 한 번에 실행

**화면:** `3. 한 번의 실행` 표와 터미널

발표에서는 202개 전체를 다시 수집하지 않습니다. 실제 저장 데이터 중 CPI 2026년 7월 발표와 NVDA 한 종목을 선택해 한 명령으로 다시 계산했습니다.

입력은 발표 1회와 종목 1개입니다. 발표 전 60분, 발표 후 5분·30분·60분의 영향 4행을 다시 계산하고 전략 결과 1행을 Upsert했습니다. 그다음 방금 저장한 영향 4행과 1분·3분·5분봉을 API가 다시 읽었습니다. 실제 실행 시간은 0.30초였습니다.

같은 명령을 두 번 실행해도 영향 고유키 4개와 전략 고유키 1개가 그대로였고 중복은 0이었습니다. 발표 중에는 외부 데이터 API, Kafka 대용량 재생과 증권사 주문을 호출하지 않습니다.

## 4. 대시보드에서 무엇을 봐야 하는가

**화면:** 로컬 `Macro Pulse`, CPI 2026-07·NVDA 선택

여기에서 세 부분을 구분해 봐야 합니다.

첫째, 연구 신호 `LONG`은 과거 발표 전 가격이 올랐다는 규칙의 결과일 뿐 주문이 아닙니다. 둘째, `0.4779%`는 이 과거 사례 하나를 가상으로 계산한 결과이며 실제 계좌 수익이 아닙니다. 셋째, 실제 시스템 행동은 오른쪽의 `NO_TRADE`입니다.

이 사례는 양수지만 전체 1,988개 계산 가능 결과의 평균은 약 마이너스 0.15649%입니다. 그리고 발표의 시장 전망치와 실제값 차이, 모의주문, 포지션 복구와 긴급 중지가 없습니다. 그래서 데이터와 전략 결과 검사만 통과하고 나머지 다섯 검사는 실패합니다.

1분·3분·5분 버튼을 누르면 같은 Alpaca SIP 데이터를 다른 해상도로 봅니다. 개발 중 1분봉이 319개로 보이는 문제도 찾았습니다. IEX와 재생 데이터가 SIP 기준 봉에 섞인 것이 원인이어서 조회 출처를 Alpaca SIP로 고정했고, 이 사례는 정확히 1분봉 180개로 표시됩니다.

## 5. 이전 장애 복구와 다음 단계

**화면:** `4. 부하·장애·복구`와 `7. 실전 자동매매까지 남은 단계`

이전 과제에서는 실제 SIP 체결 736만 건을 Kafka와 Spark로 처리했습니다. Spark 메모리 부족은 반복 사용하는 중간 결과를 디스크에 임시 저장하도록 바꿔 해결했고, 작업이 끝나면 해제했습니다. PostgreSQL 컨테이너를 중지한 장애는 다시 켠 뒤 실패 입력만 Upsert해 중복 0을 확인했습니다. Kafka 파티션 쏠림도 최대 97.5%에서 33.9%로 줄였습니다.

다음 단계는 바로 실계좌가 아닙니다. 먼저 전망치 대비 실제 발표값과 전략 성과를 보완합니다. 그다음 Alpaca 모의주문으로 주문 접수, 부분 체결, 재시작 후 포지션 복구와 긴급 중지를 검증합니다. 이후 Slack에서 사람이 승인하는 단계와 소액 제한 실전을 거쳐야 자동 실전으로 갈 수 있습니다.

이번 과제의 핵심은 파이프라인을 저장에서 끝내지 않고 실제 읽기 화면까지 연결했고, 자동매매 목표를 보여주면서도 현재 할 수 없는 주문은 확실히 차단했다는 점입니다. 감사합니다.

## 질문을 받았을 때 짧게 답하기

- **LONG인데 왜 주문하지 않나요?** `LONG`은 과거 데이터 규칙의 연구 신호이고, 실제 행동은 준비 검사를 통과해야 합니다. 현재 실제 행동은 `NO_TRADE`입니다.
- **선택 사례는 수익인데 전략이 실패한 건가요?** 네. 이 사례 한 개는 양수지만 전체 1,988개 평균은 약 -0.15649%라 전략 성과를 통과하지 못했습니다.
- **1분봉이 왜 181개가 아니라 180개인가요?** 조회 범위는 시작 시각을 포함하고 끝 시각을 제외하는 180분입니다. 예전 181개 설명은 양 끝 시각을 모두 포함해 센 이론값이었고, 현재 API 계약은 T-60 이상 T+120 미만입니다.
- **3분봉과 5분봉은 결측을 채운 건가요?** 아닙니다. 실제 1분봉을 묶고 부족한 묶음은 `PARTIAL`로 표시합니다.
- **API가 주문도 보내나요?** 아닙니다. 모두 GET인 읽기 전용 API이며 브로커 주문 경로와 키 입력이 없습니다.
- **0.30초 동안 무엇을 했나요?** 저장된 1분봉으로 영향 4행과 전략 1행을 다시 Upsert하고 같은 결과와 세 가지 봉을 다시 읽었습니다.
- **실전 자동매매는 언제 붙이나요?** 전략과 surprise 데이터를 보완한 뒤 모의주문·체결·복구·긴급 중지를 먼저 검증하고, 사람 승인과 소액 제한 실전을 거친 다음입니다.
