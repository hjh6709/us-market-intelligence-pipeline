# 09.07 7차시 발표 대본

> 발표 화면: `docs/serving-layer-assignment.md`, Archify 구성도, 로컬 `Macro Pulse`

## 1. 문제와 완성한 부분

**화면:** `먼저 보는 결론`과 Archify 구성도

안녕하세요. 지금까지는 경제 발표와 주가를 수집하고 PostgreSQL에 저장한 뒤 SQL과 로그로 결과를 확인했습니다. 이번에는 저장 결과를 사용자가 읽는 단계까지 연결했습니다.

구성도 위쪽은 Airflow가 공식 발표 일정, Alpaca 시장 봉, FRED·ALFRED 경제 환경을 수집하는 경로입니다. 아래쪽은 보관한 실제 SIP 체결을 Kafka와 Spark로 처리하는 부하·복구 경로입니다. 두 경로는 PostgreSQL에 저장되고, 이벤트 분석을 거쳐 FastAPI와 웹 대시보드에서 조회됩니다.

새 전략을 추가한 것은 아닙니다. 기존 결과의 마지막 출구를 만든 것입니다. 최종 목표는 자동매매지만 현재 운영 단계는 `RESEARCH_ONLY`, 실제 행동은 `NO_TRADE`입니다.

## 2. 실제 데이터와 상태의 의미

**화면:** `1. 문제와 실제 데이터` 표

범위는 2022년부터 2026년 8월까지 CPI 55회, 고용보고서 55회, PCE 55회와 FOMC 37회, 총 202회입니다. 종목은 10개라 발표·종목 조합은 2,020개입니다.

실제 공급자 요청과 페이지는 각각 404회였습니다. 이벤트별 1분봉 선택 합계는 308,512개, 일봉 선택 합계는 30,250개입니다. 1분봉으로 만든 3분봉은 112,593개, 5분봉은 70,090개입니다. 발표 시점 경제 환경은 2,020행, 발표 전후 네 구간의 분석 결과는 8,080행입니다.

이 숫자를 모두 더해 전체 원본 건수라고 말하지 않습니다. 파생 봉은 1분봉에서 만들었고, 가까운 발표는 같은 시장 시각을 공유할 수 있습니다. 별도의 원시 체결 부하 실험도 전체 프로젝트의 체결 총량이 아니라 CPI 55회와 네 종목으로 정한 검증 범위입니다.

Coverage 의미도 수정했습니다. 공급자 요청이 정상 종료됐는지와 실제 가격 봉이 몇 분 존재하는지는 다른 상태입니다. HTTP 성공, pagination 종료, 범위와 timestamp 무결성이 정상이라면 sparse bar만으로 수집 실패 처리하지 않습니다. 가격은 임의로 채우지 않고 3분·5분봉의 source count로 부족한 bucket을 남깁니다. 기존 macro 분석의 90% 규칙은 별도 분석 사용성 기준으로 유지했습니다.

## 3. 입력부터 읽기까지 한 번의 실행

**화면:** `3. 한 번의 실행` 표와 터미널

발표에서는 202개 전체를 다시 수집하지 않습니다. 저장된 CPI 2026년 7월 발표와 NVDA 한 종목을 선택했습니다.

한 명령이 저장된 1분봉을 입력으로 받아 발표 전 60분과 발표 후 5분·30분·60분의 영향 4행, 전략 결과 1행을 계산하고 Upsert합니다. 그다음 API와 같은 서빙 계층으로 영향 결과와 1분·3분·5분봉을 다시 읽습니다.

최종 리허설은 0.43초였고 영향 4행, 전략 1행, 중복 0을 확인했습니다. `/health`와 상세 API도 실제 HTTP 200이었습니다. 이 시연은 외부 데이터 API, Kafka 대용량 재생과 증권사 주문을 호출하지 않습니다.

## 4. 대시보드에서 확인할 것

**화면:** `Macro Pulse`, CPI 2026-07·NVDA

화면에서 세 값을 구분해야 합니다. `LONG`은 과거 발표 전 가격 방향으로 만든 연구 신호입니다. `0.4779%`는 선택한 과거 사례 하나의 비용 차감 시뮬레이션입니다. 실제 시스템 행동은 오른쪽의 `NO_TRADE`입니다.

이 사례는 양수지만 전체 1,988개 계산 가능 결과의 평균은 약 마이너스 0.15649%입니다. 전략과 연결된 실제 모의체결, 포지션 대사와 긴급 중지를 검증하지 않았으므로 주문 준비 검사를 통과시키지 않았습니다.

이 화면의 1분봉은 T-60 이상 T+120 미만인 180분 조회입니다. 반면 수집 작업은 T-60부터 T+120 timestamp까지 포함하도록 T+121 미만을 요청해 후보 시각이 181개입니다. 공급자가 모든 후보 분에 봉을 주어야 수집 성공인 것은 아닙니다.

## 5. 장애 복구와 다음 단계

**화면:** `4. 부하·장애·복구`와 `7. 남은 문제`

기존 부하 실험에서는 범위를 정해 보관한 실제 SIP 체결을 Kafka와 Spark로 처리했습니다. 발행·수신·Spark 입력이 일치했고, 잘못된 중복 판정은 거래소를 식별자에 추가한 뒤 0건이 됐습니다. Spark heap 오류는 반복 데이터의 임시 저장을 디스크로 바꿔 해결했습니다. PostgreSQL 컨테이너 장애는 재시작 뒤 실패 입력만 Upsert해 중복 0을 확인했습니다. 파티션 시험은 별도 118,118건에서 최대 비중을 97.5%에서 33.9%로 낮췄습니다.

다만 202×10 전체 Airflow 실행의 기존 `COMPLETE` 분류는 coverage 수정 전 기록입니다. 실행 성공과 건수는 유효하지만 새 수집/관측 계약으로 상태를 다시 기록해야 합니다. 이번 수정은 전체 전략과 백테스트를 다시 계산하지 않았습니다.

다음에는 전체 상태 재검증, 발표 당시 전망치와 최초 발표값, 비발표일 비교군, odd-lot 포함 봉 비교를 진행해야 합니다. 그다음 전략과 연결된 모의체결·포지션 복구·위험 한도·긴급 중지를 검증해야 합니다.

이번 과제의 핵심은 수집에서 분석과 실제 조회까지 한 흐름으로 연결하고, 데이터 품질과 현재 자동매매 한계를 화면과 증거로 명확히 보여준 것입니다. 감사합니다.

## 질문을 받았을 때 짧게 답하기

- **LONG인데 왜 주문하지 않나요?** 과거 데이터 규칙의 연구 신호일 뿐입니다. 실제 행동은 준비 검사를 통과하지 못해 `NO_TRADE`입니다.
- **선택 사례는 수익인데 전략이 실패한 건가요?** 네. 이 사례는 양수지만 전체 1,988개 평균이 약 -0.15649%입니다.
- **180분과 181개 중 무엇이 맞나요?** 둘 다 다른 계약입니다. 수집은 181개 후보 timestamp를 요청하고, 서빙 차트는 끝 시각을 제외한 180분을 보여줍니다.
- **빈 분은 수집 실패인가요?** 아닙니다. 정상 응답에서도 가격 봉이 없을 수 있습니다. 요청 완료와 관측 봉 밀도를 따로 기록합니다.
- **3분봉과 5분봉은 결측을 채웠나요?** 아닙니다. 실제 1분봉만 묶고 source count와 `PARTIAL`을 보존합니다.
- **API가 주문도 보내나요?** 아닙니다. 서빙 API는 읽기 전용이며 브로커 주문 경로가 없습니다.
- **0.43초 동안 무엇을 했나요?** 저장된 한 발표·한 종목을 다시 계산·Upsert한 뒤 같은 서빙 계층과 HTTP API로 재조회했습니다.
- **202×10 상태도 새 계약으로 검증됐나요?** 아직 아닙니다. 기존 실행·건수 증거는 유지되지만 새 계약 상태 재검증이 필요합니다.
- **odd lot을 제외하는 것이 오류인가요?** 공급자 가격 봉과 맞추는 정책이지만 전체 체결 활동을 뜻하지는 않습니다. 포함 봉과 별도 활동 통계 비교가 다음 작업입니다.
