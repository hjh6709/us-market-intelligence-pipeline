# Historical Trade Replay 100x 파일럿

- 실행일: 2026-08-24 KST
- 환경: Kafka single broker, Spark local `[2]`, PostgreSQL
- 데이터: Alpaca Historical Trades API의 실제 IEX `SMH` 거래
- 구간: `2026-08-19T19:45:00Z` 이상, `20:00:00Z` 미만
- Topic: `raw.market.v1`
- trace: `load-20260824-smh-100x`
- 상태: 100x 파일럿 완료, 1x·10x·50x 비교는 미완료

API key, 원본 payload, 정확한 시장 가격 행과 Spark checkpoint는 Git에 포함하지 않는다.

## 실행 명령

Spark를 새 checkpoint와 `startingOffsets=latest`로 먼저 실행했다.

```bash
.venv/bin/python -m src.spark_market_processor \
  --starting-offsets latest --symbols SMH --watermark "2 minutes" \
  --checkpoint-root .spark-checkpoints/load-20260824-100x --timeout 120
```

과거 실제 거래의 event-time 간격을 100배 빠르게 재생했다.

```bash
.venv/bin/python -m src.historical_market_replay \
  --symbol SMH --start 2026-08-19T19:45:00Z \
  --end 2026-08-19T20:00:00Z --feed iex \
  --trace-id load-20260824-smh-100x --speed-multiplier 100
```

같은 trace의 Kafka 메시지만 세어 Producer 건수와 대조했다.

```bash
.venv/bin/python -m src.kafka_trace_consumer \
  --trace-id load-20260824-smh-100x \
  --expected-count 1523 --timeout 60
```

## 결과

| 단계 | 결과 |
| --- | ---: |
| Alpaca API 조회 | 1,523건 |
| Kafka Producer 발행 | 1,523건 |
| Producer 소요 시간 | 8.981707초 |
| Producer 처리량 | 169.567 events/s |
| Kafka Consumer 수신 | 1,523건 |
| Spark source 입력 | 1,523건 |
| Spark validation 오류 | 0건 |
| 확정 봉 반영 거래 | 722건 |
| PostgreSQL final 1분봉 | 12행 |
| 중복 business key | 0개 |

Spark checkpoint source offset은 `0 → 1,523`으로 증가했다. PostgreSQL 확정 봉은 `19:45Z`부터 `19:56Z`까지 저장됐다. 입력과 확정 봉 반영 건수의 차이 801건은 직접 센 drop 건수가 아니라 `1,523 - 722`로 계산한 값이다. validation 오류가 0건이고 append mode는 watermark를 통과한 window만 저장하므로, 종료 시 미확정 window에 남은 건수로 추정한다.

Producer 시작 직후 Kafka idempotent producer가 `Coordinator load in progress`를 한 번 보고했지만 자동 재시도 후 delivery flush까지 완료됐고 발행·수신 건수 차이는 0건이었다.

## 해석과 남은 검증

이 결과는 100x에서 실제 trade 1,523건이 유실 없이 Kafka와 Spark에 도달하고 PostgreSQL business key 중복 없이 저장된 파일럿 증거다. 아직 Spark 처리량 한계나 100x의 우수성을 입증한 비교 실험은 아니다.

다음 실행에서는 같은 고정 구간과 환경에서 1x·10x·50x·100x를 각 3회 측정하고 Producer 처리량뿐 아니라 Kafka lag, Spark batch duration·processing rate, DB write latency, CPU와 memory를 같은 run ID로 기록한다.
