# 08.31 5차시 발표 대본

> 예상 시간: 약 4분  
> 발표 화면: [`load-recovery-assignment.md`](load-recovery-assignment.md)

## 1. 과제 목표

**화면:** `한눈에 보는 결과`

안녕하세요. 이번 과제에서는 지금까지 만든 `Kafka → Spark → PostgreSQL` 파이프라인에 실제로 더 많은 데이터를 넣어보고, 장애가 생겼을 때 다시 실행해도 데이터가 빠지거나 중복되지 않는지 확인했습니다.

기준 데이터는 이전 과제에서 사용한 2026년 8월 12일 CPI 발표 구간입니다. SPY, QQQ, SMH, NVDA 네 종목의 실제 SIP 체결 118,118건입니다.

부하 데이터는 같은 조건을 2022년부터 2026년 8월까지 실제 CPI 발표 55회로 늘렸습니다. 총 220개 구간이고, 원시 체결은 7,360,804건입니다. 기준보다 약 62배 많습니다.

## 2. 데이터와 경제지표

**화면:** `어떤 데이터를 사용했는가`

외부 Alpaca API에 736만 건을 계속 요청한 것은 아닙니다. 실제 Historical SIP 체결을 한 번만 받아 Parquet으로 저장했고, 부하 테스트에서는 저장한 파일을 Kafka에 다시 넣었습니다. 그래서 외부 서비스에는 부하를 주지 않았습니다.

경제지표도 같이 연결했습니다. FRED와 ALFRED에서 CPI, 근원 CPI, PCE, 고용, 기준금리, 2년물과 10년물 국채금리, VIX까지 10개 지표를 가져왔습니다. 월별 지표는 당시 공개된 vintage를, 일별 금리와 VIX는 발표 전날까지의 값만 사용했습니다. 55회 × 10개로 550행을 저장했고 미래 값이 연결된 경우는 0건입니다.

여기서 기준 이벤트는 CPI 55회입니다. 10개 경제지표는 각각의 발표일을 분석한 것이 아니라, CPI가 발표된 당시 시장이 알고 있던 배경 정보로 연결했습니다.

## 3. 기준과 부하 결과

**화면:** `정상 기준 실행`과 `더 많은 데이터 실행`

전체 흐름은 `저장 원본 → Kafka → Spark → PostgreSQL`입니다.

기준 118,118건은 Kafka 발행과 수신, Spark 입력이 모두 같았고 472개 1분봉으로 저장됐습니다.

전체 7,360,804건도 세 단계의 건수가 모두 같았습니다. 형식 오류는 0건이었습니다. Spark가 원본에서 event ID가 같은 거래 49건을 찾아 한 번만 남겼고, 최종적으로 22,260개 1분봉을 PostgreSQL에 저장했습니다. DB 고유키 중복은 0건입니다.

1분봉 수가 이론상 최대치보다 적은 이유도 확인했습니다. 한 분에 Odd Lot만 있으면 원시 거래와 거래량은 존재하지만 가격을 만들 수 없어 완성된 OHLCV 행은 저장하지 않습니다. 거래 원본이 사라진 것은 아니며, 이후에는 1분봉을 보존한 상태에서 분석용 5분봉과 coverage를 추가할 계획입니다.

GCP 전체 실행 시간은 약 28분 10초였습니다. 사용한 VM은 4 vCPU와 16GB 메모리입니다.

실행하면서 병목도 발견했습니다. 처음 로컬 실행은 Spark가 중간 데이터를 메모리에 올리다가 heap 부족으로 실패했습니다. 그래서 중간 데이터를 디스크에 저장하고 Spark heap을 6GB로 지정한 뒤 같은 입력을 다시 실행해 성공했습니다.

또 종목코드를 Kafka key로 사용하니 세 파티션 중 하나에 데이터가 약 97퍼센트 몰렸습니다. 순서는 유지됐지만 병렬 처리에는 불리했습니다. 다음에는 종목과 발표일을 합친 key를 시험할 계획입니다.

## 4. 장애와 복구

**화면:** `PostgreSQL 적재 실패`

대표 장애로 GCP의 PostgreSQL 컨테이너만 중지했습니다.

이 상태에서도 Kafka는 118,118건을 모두 발행하고 수신했지만 DB 연결이 거부돼 저장은 0건이었고, 실행 상태도 성공이 아니라 실패로 기록됐습니다.

그다음 PostgreSQL을 다시 시작하고 정상 상태를 확인한 뒤 같은 입력을 다시 실행했습니다. 472개 1분봉이 Upsert됐지만 전체 행은 장애 전과 같은 22,260개였습니다. 같은 데이터를 새 행으로 또 넣지 않았기 때문입니다. 최종 고유키 중복도 0건이었습니다.

추가로 외부 API 대신 mock 503을 한 번 발생시킨 뒤 재시도로 정상 응답을 받는 과정과, 잘못된 입력을 수정해 다시 실행하는 과정도 확인했습니다.

## 5. 정리

**화면:** `과제 요구사항 확인`

정리하면 기준보다 약 62배 많은 실제 거래를 처리했고, Kafka 누락 0건, Spark 형식 오류 0건, DB 고유키 중복 0건을 확인했습니다. DB 장애도 실패로 정확히 기록하고 같은 입력으로 복구했습니다. 동일 입력을 다시 처리한 전후에는 1분봉 행 수뿐 아니라 OHLC와 거래량을 포함한 결과 hash도 같았습니다.

이번 과제로 단순히 많은 데이터를 처리한 것뿐 아니라, 메모리 부족과 Kafka 파티션 쏠림이라는 실제 병목도 찾았습니다. 다음에는 파티션 key를 개선하고 Airflow에서 실패한 파티션만 다시 실행하도록 연결하겠습니다. 감사합니다.
