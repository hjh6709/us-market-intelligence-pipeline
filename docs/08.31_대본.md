# 08.31 5차시 발표 대본

> 예상 시간: 약 4분  
> 발표 화면: [`load-recovery-assignment.md`](load-recovery-assignment.md)

## 1. 무엇을 시험했는가

**화면:** `발표할 때 먼저 말할 핵심`과 `한눈에 보는 결과`

안녕하세요. 이번 과제에서는 지금까지 만든 데이터 파이프라인에 평소보다 많은 데이터를 넣고, 처리 중 장애가 발생해도 복구 후 데이터가 빠지거나 중복되지 않는지 확인했습니다.

실험 대상은 외부 Alpaca API가 아니라, 이미 수집해 둔 실제 SIP 체결을 처리하는 **Kafka → Spark → PostgreSQL 내부 경로**입니다.

기준 실행은 2026년 8월 12일 CPI 발표 전후 121분 동안의 SPY, QQQ, SMH, NVDA 네 종목입니다. 원시 체결은 118,118건입니다.

부하 실행은 같은 조건을 2022년 1월부터 2026년 8월까지 CPI 발표 55회로 넓혔습니다. 220개 구간, 총 7,360,804건으로 기준보다 약 62배 많습니다.

## 2. 어떤 데이터가 흐르는가

**화면:** `전체 아키텍처`와 `어떤 데이터를 사용했는가`

먼저 Alpaca Historical Trades API로 220개 구간의 실제 SIP 체결을 사전에 수집해 Parquet 원본으로 보관했습니다. 부하 실험에서는 API를 다시 호출하지 않고 이 파일을 Kafka에 넣었습니다. 따라서 외부 서비스에 부하를 보낸 것이 아닙니다.

Spark는 개별 체결의 형식과 필수값을 검사하고, 같은 event ID를 한 번만 남긴 뒤 종목별 1분봉으로 집계합니다. 결과는 PostgreSQL에 Upsert합니다.

CPI 발표일은 BLS에서 확인하고, FRED와 ALFRED의 10개 지표를 각 CPI 시점의 배경 정보로 연결했습니다. 분석 이벤트는 CPI 55회이고, 550행은 55회에 10개 지표를 연결한 결과입니다.

## 3. 기준 실행과 부하 실행 결과

**화면:** `정상 기준 실행`과 `더 많은 데이터 실행`

기준 실행에서는 원시 입력, Kafka 발행, Kafka 수신, Spark 입력이 모두 118,118건으로 일치했습니다. Spark가 472개의 1분봉을 만들어 PostgreSQL에 저장했고, 전체 시간은 약 76.5초였습니다.

부하 실행에서도 원시 입력, Kafka 발행, Kafka 수신, Spark 입력이 모두 7,360,804건으로 일치했고 형식 오류는 0건이었습니다. 다만 이후 전체 흐름을 점검하면서 기존 코드가 거래소가 다른 체결 49건을 중복으로 잘못 판단한 것을 발견했습니다. 식별키에 거래소를 추가해 전체를 다시 처리한 결과 실제 중복은 0건이었고, 최종 1분봉은 22,260개, PostgreSQL 고유키 중복은 0건입니다.

전체 실행 시간은 약 28분 10초였고 평균 처리량은 초당 약 4,355개 체결입니다. 기준 실행에는 최초 Spark 준비 시간이 포함돼 있어 두 시간을 단순 비례 성능으로 비교하지는 않았습니다.

각 구간은 이론상 121분이지만 항상 121개의 1분봉이 생기지는 않습니다. 한 분에 Odd Lot 체결만 있으면 원시 거래는 보존되지만, provider 규칙상 가격을 만들 수 없어 `market_bars` 행은 저장하지 않습니다. 이것은 수집 누락이 아니라 무가격 구간입니다.

현재 구현 결과는 1분봉이며, 3분봉과 5분봉은 아직 저장하지 않았습니다.

## 4. 부하에서 발견한 문제와 수정

**화면:** `실제로 발견한 병목`

처음 로컬에서 전체 데이터를 실행했을 때 Spark가 중간 결과를 RAM에 보관하다 `Java heap space`로 종료됐습니다. 그래서 중간 결과를 디스크에 두는 `DISK_ONLY`로 바꾸고, GCP의 Spark Driver heap을 6GB로 지정했습니다.

6GB는 디스크가 아니라 16GB RAM 중 Spark Java 프로세스가 쓰는 상한입니다. VM은 4 vCPU, 16GB RAM, 100GB 디스크였고, 디스크에는 Parquet 원본과 Kafka·DB 파일, Spark 중간 결과가 함께 저장됐습니다.

수정 후 같은 7,360,804건을 끝까지 처리해 22,260개의 1분봉을 저장했습니다.

Kafka는 종목코드를 key로 사용하자 세 파티션 중 하나에 누적 메시지의 약 97.5%가 몰렸습니다. 누락은 없었지만 병렬 처리에는 불리해, 다음에는 `종목 + CPI 발표일` key를 비교할 계획입니다.

## 5. 장애와 복구

**화면:** `PostgreSQL 적재 실패`와 `누락과 중복을 어떻게 확인했는가`

장애 실험에서는 GCP의 PostgreSQL만 중지하고 기준 데이터를 다시 실행했습니다. Kafka 발행과 수신은 118,118건이었지만 DB 저장은 0건이었고, 실행 상태도 `failed`로 남았습니다.

PostgreSQL을 다시 시작하고 같은 입력을 재실행하자 472개 1분봉이 Upsert됐습니다. 기존 행의 고유키와 같기 때문에 전체 행 수는 22,260개로 유지됐고, 중복 key도 0건이었습니다.

GCP 장애 복구에서는 최종 행 수와 중복 key를 확인했습니다. 별도의 로컬 동일 입력 재실행에서는 OHLC, 거래량, 거래 건수와 VWAP으로 만든 결과 hash도 전후 동일한지 확인했습니다.

추가로 mock API 503 재시도, 잘못된 입력과 DB 주소도 안전하게 재현했습니다.

## 6. 마무리

**화면:** `과제 요구사항 확인`

정리하면 기준보다 약 62배 많은 실제 체결을 GCP에서 처리했고, Kafka 발행·수신·Spark 입력 건수가 모두 일치했습니다. Spark 메모리 부족은 디스크 기반 중간 저장으로 수정해 같은 전체 입력으로 성공했습니다.

또 PostgreSQL 장애를 실패로 정확히 기록하고, 복구 후 같은 데이터를 재실행해 최종 22,260행, 고유키 중복 0건과 동일한 결과 hash를 확인했습니다.

다음에는 Kafka key를 개선하고, Airflow에서 실패한 발표일과 종목 구간만 선택해 재실행하도록 연결하겠습니다. 감사합니다.

## 질문이 나오면 답할 핵심

- **6GB가 전체 메모리인가요?** 아니요. VM은 RAM 16GB이고, 6GB는 그중 Spark Driver Java heap의 상한입니다. 디스크는 100GB입니다.
- **736만 건을 Alpaca API에 반복 요청했나요?** 아니요. 수집 단계에서는 구간과 pagination에 따라 여러 API 요청을 했지만, 부하·복구 실험에서는 저장한 실제 SIP 체결만 Kafka에 재생했습니다.
- **왜 1분봉이 최대 개수보다 적나요?** 원시 거래가 없거나 Odd Lot처럼 OHLC 가격을 만들지 않는 체결만 있는 분에는 완성된 1분봉을 만들지 않기 때문입니다. 원본 체결은 보존됩니다.
- **DB 장애 JSON의 Spark 수치 0은 Spark가 아무것도 읽지 않았다는 뜻인가요?** 아니요. DB 예외 때문에 Spark 요약값이 반환되지 않아 실패 결과 기본값 0이 기록된 것입니다. 이 실험에서 확정한 것은 Kafka 118,118건, DB 저장 0건과 `failed` 상태입니다.
- **3분봉·5분봉도 저장했나요?** 아니요. 현재 구현과 검증 결과는 1분봉이며 5분봉은 다음 계획입니다.
- **경제지표 550개를 각각 이벤트로 분석했나요?** 아니요. 이벤트는 CPI 55회이고, 10개 지표를 각 CPI 시점의 배경 정보로 연결해 550행이 된 것입니다.
- **`Java heap space`는 디스크가 부족했다는 뜻인가요?** 아니요. Spark의 Java 작업 메모리가 부족했다는 뜻입니다. 중간 결과를 디스크에 저장하도록 바꿔 복구했습니다.
- **49건은 진짜 중복이었나요?** 아니요. 거래소가 다른 별개의 체결을 기존 식별키가 같은 거래로 오인한 결함이었습니다. 거래소를 식별키에 추가한 전체 재실행에서는 중복 0건을 확인했습니다.
